# 当 MySQL 大师批评我用 TEXT：一场关于数据库底层设计哲学的碰撞

### 引言：一次来自“师傅”的代码审查

前几天，我在设计一张 PostgreSQL 的新表。由于业务需求是存储来源文本，且无法预测未来的最大长度，我毫不犹豫地使用了 `TEXT` 类型（以及不带长度的 `VARCHAR`）。

然而，我的师傅在 Code Review 时狠狠地批评了我。他是一位拥有十多年经验的 MySQL 资深专家，他的原话是：“**你这种设计，磁盘占用会很大，内存缓存的负担也会极重！在 MySQL 里，绝不允许这么随便用不定长类型。**”

我陷入了沉思：难道在 PostgreSQL 里“无脑用 `TEXT`”错了吗？为什么师傅会说它会撑爆内存？随着我们深入的探讨，我才发现，这根本不是“谁对谁错”的问题，而是 **MySQL 与 PostgreSQL 在底层架构设计上的世纪大碰撞**。

今天，就把这次交流的收获整理成文，带你彻底看透 `CHAR`、`VARCHAR`、`TEXT` 在这两大主流数据库中的爱恨情仇。

---

### 一、 PostgreSQL 视角：为什么“无脑 Text”是正道？

在 PostgreSQL 的官方文档中，明确指出了 `TEXT`、`VARCHAR` 和不带长度的 `VARCHAR` 在**性能上没有区别**。它们共享同一套底层的变长存储机制。

#### 1. 存储机制：按需分配，绝不多占
无论你声明的是 `VARCHAR(16)` 还是 `TEXT`，它们在磁盘上**都只存储实际写入的内容**，外加一个极小的头部信息（记录长度）。`VARCHAR(n)` 里的 `n`，在 PG 中**不会预先占用任何空间**。

#### 2. 内存处理：拒绝“内存膨胀”
PG 在处理排序、分组等操作时，完全按实际字符串的长度来处理，**绝对不会**发生“因为声明了长度，就在内存里强行补齐”的奇葩操作。

#### 3. 定长 CHAR(n) 的末路
在 PG 中，`CHAR(n)` 才是真正“最慢”的类型。因为它是定长的，如果你存 `'abc'` 到 `CHAR(10)`，PG 会在末尾强制填充 7 个空格。这不仅浪费空间，还会导致 `LENGTH()` 函数计算出错，甚至在字符串拼接时产生不可见的“幽灵空格”。

**💡 PG 的终极结论**：在 PG 里，`VARCHAR(n)` 纯粹就是一个隐式的 `CHECK (char_length(col) <= n)` 长度约束。它不省空间、不提性能，只做业务校验。如果不设上限，直接用 `TEXT` 是最原汁原味、最推荐的做法。

---

### 二、 MySQL 视角：师傅的担忧从何而来？

师傅的批评在 MySQL 的语境下，是绝对正确的金科玉律。因为在 MySQL 里，字符串类型的行为是“精神分裂”的：

#### 1. 磁盘存储：和 PG 一样聪明
在 InnoDB 存储引擎中，`VARCHAR(255)` 同样不会预先占用物理空间，也是按实际内容存储加长度前缀。

#### 2. 内存处理：令人恐惧的“内存填充”
当 MySQL 要把数据从存储引擎层拉到 SQL 层进行 `ORDER BY` 或 `GROUP BY` 时，它为了利用定长处理的速度优势，**会把 `VARCHAR(n)` 在内存中硬生生地填充到最大长度 `n`！**
假设在 `utf8mb4` 下，你声明了 `VARCHAR(255)`，即使里面只存了 `'abc'`，在内存临时表里它也会膨胀到 **255 × 4 = 1020 字节**。这就是 MySQL 界那句著名的铁律的由来：**VARCHAR 的 N 必须尽可能小！**

#### 3. TEXT 的“原罪”：内存排斥
你可能会想，既然 `VARCHAR(n)` 会膨胀，那 MySQL 用 `TEXT` 不就没事了？
大错特错！MySQL 的 MEMORY 存储引擎（用于内存临时表）**根本不支持 `TEXT` 和 `BLOB` 类型**。这意味着，一旦你的查询包含了 `TEXT` 字段，并且需要排序或分组，MySQL 会直接放弃内存临时表，**被迫在磁盘上创建临时表**。
磁盘 I/O 的速度比内存慢几百倍，这才是师傅口中“缓存负担重、性能极差”的真正原因。

### 三、 一张表看懂世纪大碰撞

| 维度                        | 🐬 MySQL                                        | 🐘 PostgreSQL                                |
| :-------------------------- | :--------------------------------------------- | :------------------------------------------ |
| **不定长 VARCHAR 的存在性** | 必须带 `n`，不存在无长度限制的 `VARCHAR`       | 支持不带 `n` 的 `VARCHAR`，且与 `TEXT` 等价 |
| **VARCHAR(n) 磁盘占用**     | 按实际内容占用                                 | 按实际内容占用                              |
| **VARCHAR(n) 内存占用**     | 参与复杂计算时，**膨胀至最大长度 n**           | **按实际内容占用，无膨胀**                  |
| **TEXT 类型的待遇**         | **“内存临时表毒药”**，无法进入内存，直接写磁盘 | **“一等公民”**，与 `VARCHAR` 性能无异       |
| **CHAR(n) 的定位**          | 适合极短、定长、高频查询（有填充空格行为）     | 通常最慢（有填充空格行为，存在兼容包袱）    |
| **定长的 `n` 的本质**       | **内存预算指令**（决定内存膨胀上限）           | **纯业务约束**（相当于一个 CHECK 规则）     |

---

### 四、 架构差异的根源：为什么会这样？

*   **MySQL 的哲学是“简单、极速、为 OLTP 优化”**。它早期的 MEMORY 引擎设计非常简陋，只支持定长格式。为了保住单表读写极快的神话，它强迫开发者通过 `VARCHAR(n)` 控制内存边界。`TEXT` 则是专门用来兜底大文本的，牺牲其查询计算性能是默认的代价。
*   **PostgreSQL 的哲学是“标准、严谨、功能丰富”**。它底层强大的 TOAST（超大属性存储技术）机制和变长处理逻辑，天生就能优雅地处理任意长度的字符串。因此，PG 认为：长度限制属于业务逻辑，存储引擎不需要用“预设长度”来干涉数据的流转。

---

### 五、 结语：到底该怎么选？

这场争论没有输家，它只教会了我一个深刻的道理：**脱离了数据库底层架构去谈代码规范，都是耍流氓。**

现在的我，在面对建表时，会这样思考：

1.  **如果我在写 MySQL**：我会像师傅教导的那样，精打细算。对于核心业务字段，严格评估并设置合理的 `VARCHAR(n)`，绝不允许异常数据撑爆内存；只有文章正文、日志等大段文本才用 `TEXT`。
2.  **如果我在写 PostgreSQL**：我会拥抱 `TEXT`。默认全部用 `TEXT`（或不定长 `VARCHAR`），只有在业务明确要求“手机号必须是 11 位”时，才顺手加个 `VARCHAR(11)` 或 `CHECK` 约束。

技术没有绝对的对错，只有场景的适配。理解了 MySQL 的“内存填充”，也理解了 PG 的“原生变长”，你才能真正算得上是掌握了数据库的工程师。

（下次再被师傅批评，我就可以拿着这篇原理解析去和他“华山论剑”了 😎）
