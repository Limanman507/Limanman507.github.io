# [网络]一次 Docker 拉镜像失败，让我从零搞懂了 DNS

## 前言

这是我学习过程中记录的一篇故障复盘。我不是网络科班出身，所以这篇博客会尽量从“新手会问什么”的角度写，而不是一上来就堆命令和术语。

事情的起因很简单：服务器上 `docker pull` 拉镜像失败。最开始我以为是 Docker 的问题，后来才发现，真正坏掉的是**宿主机的域名解析**。

这次排查让我第一次真正理解了几个东西：

- 为什么 `ping IP` 通，`ping 域名` 却失败？
- `127.0.0.53` 到底是什么？
- 为什么改 Docker 的 `daemon.json` 没用？
- `systemd-resolved` 和 `/etc/resolv.conf` 软链接分别管什么？
- `#DNS=` 是默认配置吗？为什么默认值也能正常工作？

下面按过程、解法、知识点三部分记录。

---

## 一、故障过程

### 1. 现象

在服务器上执行 `docker pull` 时，报错大意是：

```text
dial tcp: lookup registry-1.docker.io on 127.0.0.53:53: server misbehaving
```

同时在终端执行：

```bash
ping www.baidu.com
```

提示域名解析暂时失败。

但是直接 ping 公网 IP：

```bash
ping 223.5.5.5
```

网络是通的。

### 2. 第一次踩坑：改 Docker 的 daemon.json

一开始以为是 Docker DNS 配置问题，于是修改 `/etc/docker/daemon.json`，加上：

```json
"dns": ["223.5.5.5", "114.114.114.114"]
```

然后重启 Docker。结果依然报错，`docker info` 里也看不到生效的 DNS。

**为什么没用？**

因为 `daemon.json` 里的 `"dns"` 字段，主要作用是：**Docker 启动容器时，把 DNS 写进容器内部的 `/etc/resolv.conf`**。它管的是“容器里面”，不是“宿主机自己”。

而 `docker pull` 是谁在干活？是宿主机上的 **Docker 守护进程（Daemon）**。它拉镜像前，必须先使用**宿主机自己的网络和 DNS** 去解析 `registry-1.docker.io`。宿主机 DNS 已经瘫痪，给容器配再多 DNS 也救不了它。

打个比方：

> 大楼总前台坏了，快递员进不来。你给每个小房间配了电话簿，但快递员在大楼门口问路时还是没人能告诉他地址。

### 3. 确认故障层面

现象组合起来已经很说明问题：

- `ping 223.5.5.5` 通 → 公网 IP 连通性正常，线路没断。
- `ping www.baidu.com` 失败 → 域名解析失败。
- Docker 报错指向 `127.0.0.53:53` → 本机 DNS 入口出问题。

所以故障不在 Docker 本身，而在**宿主机的 DNS 解析链路**。

---

## 二、根因分析：其实没有完全定位唯一根因

这里要特别诚实地说一句：**这次修复是“组合修复”，严格说没有留下证据证明唯一根因。**

能确定的是：

- 宿主机 DNS 解析层坏了。
- `systemd-resolved` 管理的本机 DNS 入口 `127.0.0.53` 无法正常完成解析。
- Docker 只是最早暴露问题的程序之一。

但不能完全确定的是：

- 是 `systemd-resolved` 没配上游 DNS？
- 还是 `/etc/resolv.conf` 指向的目标失效？
- 还是服务本身异常？
- 还是多个问题叠加？

因为修复时同时做了三件事，最后恢复了，但无法单独归因。这一点后面会详细讲。

---

## 三、修复方案

修复在系统层完成，主要动作是：

1. 修改 `/etc/systemd/resolved.conf`，指定上游 DNS：

```text
DNS=223.5.5.5 114.114.114.114
```

2. 备份并重建 `/etc/resolv.conf` 软链接，指向：

```text
/run/systemd/resolve/resolv.conf
```

3. 重启 `systemd-resolved`：

```bash
sudo systemctl restart systemd-resolved
```

修复后，不只是 Docker，`apt`、`curl`、Python 请求等所有依赖域名解析的程序都恢复正常。现有业务容器没有受影响，也不需要重启服务器。

## 四、每个步骤涉及的知识科普

这一部分是重点，基本覆盖了我这次真正搞不懂的问题。

### 知识点 1：IP、域名、DNS 分别是什么？

- **IP 地址**：像门牌号，比如 `223.5.5.5`。
- **域名**：像店名，比如 `www.baidu.com`、`registry-1.docker.io`。
- **DNS**：像电话簿/问路系统，负责把域名翻译成 IP。

所以：

- `ping 223.5.5.5` 成功 → 路是通的，门牌号能找到。
- `ping www.baidu.com` 失败 → 问路系统坏了，不知道店名对应哪个门牌号。

### 知识点 2：`127.0.0.53` 是什么？

`127.0.0.1` 一般表示“本机自己”，`127.0.0.53` 也属于本机回环地址，不是公网 DNS。

Ubuntu 使用 `systemd-resolved` 管理 DNS 时，会在本机开一个 DNS 入口，地址就是 `127.0.0.53`。程序先问它，它再帮你往外问。

所以报错：

```text
lookup registry-1.docker.io on 127.0.0.53:53: server misbehaving
```

意思是：Docker 去问本机 DNS 入口，但这个入口没正常干活。

### 知识点 3：`systemd-resolved` 是什么？

可以理解成 Ubuntu 自带的 **DNS 管家 / 总前台**。

- 它在后台运行。
- 它监听 `127.0.0.53:53`。
- 程序来问域名，它接住。
- 自己不知道答案时，转发给“上游 DNS”，比如 `223.5.5.5`。

正常链路：

```text
程序 -> 127.0.0.53（systemd-resolved）-> 上游 DNS -> 互联网
```

这次故障就出在这个管家身上。

### 知识点 4：`223.5.5.5` 和 `114.114.114.114` 是什么？

它们是两个**免费、公开、稳定的公共 DNS 服务器**。

| DNS 地址          | 提供方             | 特点                                 |
| :---------------- | :----------------- | :----------------------------------- |
| `223.5.5.5`       | 阿里云             | 节点多，国内解析快，稳定性好         |
| `114.114.114.114` | 国内运营商联合推出 | 覆盖广，稳定，有一定恶意网站拦截能力 |

同时配两个，是一种**冗余备份**：一个没响应，可以问另一个。

### 知识点 5：为什么配上这两个地址就能修好？

`resolved.conf` 里的 `DNS=`，作用是给 `systemd-resolved` 指定“上游 DNS”：

> “你自己不知道答案时，就去问 `223.5.5.5` 和 `114.114.114.114`。”

所以修复的本质是：**给本机 DNS 管家接通了外部电话线**，不是把管家拆掉换成阿里云。

### 知识点 6：`#DNS=` 是默认配置吗？为什么默认也能工作？

是的，`#DNS=` 是 Ubuntu 24.04 中 `resolved.conf` 的默认状态。`#` 表示这一行被注释，**选项没有设置，值为空**。

但 `DNS=` 为空并不代表 DNS 一定瘫痪。`systemd-resolved` 会按优先级自动找可用 DNS：

1. 网络接口通过 DHCP 自动获取的 DNS；
2. `/etc/resolv.conf` 里配置的 DNS；
3. 内置的 `FallbackDNS` 备用 DNS。

这台服务器的问题是：**自动获取这条链路也断了**，所以管家手里没有任何可用上游，只能报错。手动写 `DNS=` 相当于强制指定一个可靠起点，绕过失效的自动获取。

### 知识点 7：`/etc/resolv.conf` 和软链接是什么？

`/etc/resolv.conf` 是系统里的一张“小纸条”，告诉程序：

> 你要查域名，去问哪个 DNS 服务器。

软链接类似 Windows 的快捷方式。Ubuntu 上 `/etc/resolv.conf` 常见有两种指向：

**A. stub 模式（默认常见）：**

```text
/etc/resolv.conf -> /run/systemd/resolve/stub-resolv.conf
内容：nameserver 127.0.0.53
```

程序问本机 DNS 管家。

**B. 直连上游模式：**

```text
/etc/resolv.conf -> /run/systemd/resolve/resolv.conf
内容：nameserver 223.5.5.5 等真实上游地址
```

程序直接问上游 DNS。

报告里的修复，是把软链接改成指向 B。**注意：指向 stub 本身不一定是错误**，它是 Ubuntu 的正常设计。它是否“失效”，要看背后的 `127.0.0.53` 是否真的在正常服务。

### 知识点 8：这次修复其实是两个角度

可以把修复组合拳归纳为两个角度：

| 角度               | 动作                                 | 解决链路哪一段                     |
| :----------------- | :----------------------------------- | :--------------------------------- |
| 角度一：配上游 DNS | 在 `resolved.conf` 写 `DNS=...`      | 让 DNS 管家知道往外问谁            |
| 角度二：重建软链接 | 让 `/etc/resolv.conf` 指向有效配置   | 决定程序读哪张纸条、走哪条解析路径 |
| 动作：重启服务     | `systemctl restart systemd-resolved` | 让配置真正加载生效                 |

重启只是执行动作，不算独立角度。

### 知识点 9：为什么无法确定是哪一步修好的？

因为三步同时做，最后恢复了，但没有留下修复前证据。可能的情况包括：

| 可能原因             | 只配上游 + 重启够不够 | 需不需要改软链接 |
| :------------------- | :-------------------- | :--------------- |
| 只是没配上游 DNS     | 够                    | 不需要           |
| 软链接指向失效目标   | 不够                  | 需要             |
| 服务异常，重启后恢复 | 可能够                | 不一定           |
| 多个问题叠加         | 都需要                | 需要             |

如果原来 `/etc/resolv.conf` 指向正常，只是没配上游 DNS，那么**只配上游 DNS + 重启，理论上就够了，新软链接大概率不需要**。

### 知识点 10：DNS 解析的完整过程

以解析 `registry-1.docker.io` 为例：

1. Docker 守护进程问本机 `127.0.0.53`：这个域名 IP 是多少？（递归查询，期望最终答案）
2. `systemd-resolved` 查缓存，没有就转发给上游 DNS，比如 `223.5.5.5`。
3. 上游 DNS 进行迭代查询：问根服务器 → 问 `.io` 权威服务器 → 问 `docker.io` 权威服务器 → 拿到最终 IP。
4. 答案返回给 `systemd-resolved`，它缓存后返回给 Docker。

**递归**体现在程序对本地解析器的信任；**迭代**发生在本地解析器与外部 DNS 之间逐级问路。

### 知识点 11：镜像加速器为什么当时也没救回来？

国内镜像加速器仍然需要先解析加速器域名，再连接 IP 下载。宿主机 DNS 瘫痪时，加速器域名也解析不了，所以照样失败。宿主机 DNS 修好后，加速器才真正发挥作用。

### 知识点 12：`daemon.json` 里的 DNS 还要保留吗？

建议保留。虽然它没修好宿主机 DNS，但它能保证以后启动的**容器内部**拥有稳定 DNS。它和宿主机 DNS 是两层东西。

## 五、以后遇到类似问题怎么排查？

给新手的简单顺序：

1. `ping 223.5.5.5`：公网 IP 通不通？
2. `ping www.baidu.com`：域名解析正不正常？
3. 看 `/etc/resolv.conf`：系统让程序去问谁？
4. 如果是 Ubuntu，检查 `systemd-resolved` 状态和上游 DNS 配置。
5. 再回头看 Docker：`docker pull` 失败到底是 DNS 问题，还是仓库连接问题。

如果以后想真正定位唯一根因，修复前应先记录：

```bash
systemctl status systemd-resolved
resolvectl status
resolvectl query registry-1.docker.io
readlink -f /etc/resolv.conf
cat /etc/systemd/resolved.conf
journalctl -u systemd-resolved --no-pager
ss -lunpt | grep 53
```

这些能帮助区分：服务是否运行、`127.0.0.53:53` 是否监听、上游是否配置、软链接指向哪里、具体报什么错。

---

## 六、我学到的 6 件事

1. **ping IP 通，不代表 DNS 正常；ping 域名失败，先查 DNS。**
2. **域名是名字，IP 是门牌号，DNS 是翻译系统。**
3. **`127.0.0.53` 是本机 DNS 入口，不是公网 DNS。**
4. **Docker 拉镜像时，先由宿主机 Docker 守护进程解析域名；宿主机 DNS 坏了，容器 DNS 配置救不了它。**
5. **`daemon.json` 里的 `"dns"` 主要管容器内部，不管宿主机自己。**
6. **组合修复能恢复服务，但不等于定位了唯一根因。修复前留证据，比修复本身更重要。**

---

## 七、总结

这次故障最重要的结论是：

> 不是 Docker 单独坏了，而是宿主机的域名解析系统坏了。Docker 只是最早暴露问题的程序之一。

修复可以归纳为两个角度：**给 DNS 管家配上游** + **决定程序读哪张 DNS 配置纸条**。重启服务只是让配置生效。

但严格说，这次是组合修复，没有留下修复前完整证据，所以无法确定唯一根因。这也是我这次学到的最有价值的一课：**排查问题时，先记录现场，再动手修复。**
