# [数据库]AI让我在PG里用TEXT，MySQL大师却骂了我一顿：一场关于“约束”的底层觉醒

### 引子：被AI“坑”了的新手

事情是这样的，我最近接到了一个基于 PostgreSQL 建表的工作任务。

面对那些不知道未来会存多长内容的文本字段（比如备注、描述、来源明细），我习惯性地求助了 GPT 和 Claude。AI 的回答极其一致且自信：“在 PostgreSQL 中，保存相同内容时，`TEXT` 通常不会比 `VARCHAR` 更慢，也不会更占空间。建议直接使用 `TEXT` 或不带长度的 `VARCHAR`，避免人为长度限制影响完整入库。”

听起来简直完美！于是我欣然地准备在 DDL 里大干一场。

然而，当我把这版设计拿给我的师傅（一位拥有十几年经验的 MySQL 资深专家）看时，被劈头盖脸地批评了一顿：“**你这种设计，磁盘占用会很大，内存缓存的负担也会极重！**”

迫于师傅的威严和工作任务的压力，我默默改回了师傅建议的 `varchar(64)`、`varchar(1024)` 等带长度限制的写法。

但回过头来，我心里犯起了嘀咕：GPT 和 Claude 两个顶级 AI，加上 PostgreSQL 官方文档的背书，难道全错了？为了搞清楚这背后的逻辑，我深挖了一下 MySQL 和 PostgreSQL 的底层架构，结果发现了一个让我彻底顿悟的“新大陆”。

---

### 第一幕：深挖底层，发现两个平行宇宙

作为新手，我一开始以为 `varchar(n)` 只是限制长度，`text` 是不限长度，底层存储差不多。但事实上，MySQL 和 PostgreSQL 在这块的设计理念，简直是两个平行宇宙。

#### 1. MySQL：精打细算的“强迫症”
在 MySQL 里，你根本没有“不限定长度的 `VARCHAR`”这个选项，必须得带上 `(n)`。为什么师傅强调长度会影响内存和缓存？

*   **磁盘上很聪明**：`VARCHAR(n)` 和 `TEXT` 在磁盘上都只存实际内容，不预分配。
*   **内存里很坑爹**：当 MySQL 执行排序（`ORDER BY`）、分组（`GROUP BY`）生成**内存临时表**时，它为了处理定长方便，**会把 `VARCHAR(n)` 在内存里直接补齐到最大长度 `n`**！如果你声明了 `VARCHAR(255)`，实际存了 3 个字符，在内存里它也会膨胀成 255 个字符。这就是师傅说的“缓存负担极重”的真相。
*   **TEXT 是内存毒药**：既然 `VARCHAR` 会膨胀，那用 `TEXT` 行不行？更惨。MySQL 的内存临时表压根**不支持 `TEXT` 类型**，一旦带了 `TEXT` 字段去排序，MySQL 只能痛苦地去建**磁盘临时表**，性能直接暴跌。

#### 2. PostgreSQL：大道至简的“自由派”
但在 PG 里，故事完全不一样。
*   **存储和内存都不膨胀**：PG 的 `TEXT` 和 `VARCHAR` 底层机制完全一样，无论在磁盘还是内存，全都按实际内容占用，毫无“补齐”的概念。
*   **临时表兼容一切**：PG 的临时表机制可以完美处理任意长度的 `TEXT`。
*   **奇妙的 `CHAR(n)`**：在 PG 里，`CHAR(n)` 反而成了最慢的类型（因为会填充空格），基本被废弃。
*   **约束的本质**：PG 里的 `varchar(n)` 和不带长度的 `varchar`、`text` 性能无差。它的存在，**纯粹是为了做“长度约束”**。

---

### 第二幕：那么，是 AI 错了，还是师傅错了？

挖到这里，结论似乎很明显了：AI 是懂 PG 的，它的建议在 PG 的体系里完全正确；师傅是懂 MySQL 的，他的建议在 MySQL 的体系里也绝对正确。

但我仔细复盘了我的建表 DDL，发现了一个致命的问题——**我确实没有做错，但我少做了一件事**。

师傅在批评我时，核心逻辑是“你太随意了，你需要对数据长度有明确的预期和限制”。而我听从 AI 的建议，去掉了长度限制（使用 `TEXT`），仅仅做到了“能不限制就不限制”，但**我没有在其他地方把约束补回来**。

问题的核心根本不在于是选 `TEXT` 还是 `VARCHAR(n)`，而在于**数据完整性约束的理念**。

---

### 第三幕：终极顿悟——“约束”无处不在

我突然明白，MySQL 的师傅和 PG 的 AI 其实在说同一件事，只不过表现形式不同：

*   **师傅（MySQL 思维）**：因为 MySQL 的 `varchar(n)` 会消耗内存，所以他把 `(n)` 当作一种强制的物理和逻辑约束。他在建表时逼着你思考：“这个字段到底最多需要多少？”这是一种极其优秀的**前置设计习惯**。
*   **我（PG 思维）**：在 PG 里，用 `TEXT` 规避内存灾难完全没问题。但**我丧失了约束的意识**。如果这是一个手机号字段，即使它用 `TEXT` 存，我也应该加一个 `CHECK (char_length(phone) = 11)`，或者在应用层做好校验。

AI 告诉我“PG 里 `TEXT` 很好”，这是**存储机制**层面的实话；
师傅批评我“缺乏长度预期”，这是**系统健壮性**层面的警钟。

**我在 PG 里用 `TEXT`，却在业务上变成了一个“来者不拒”的无底洞。这才是师傅真正担心的事情。**

---

### 写给新手：如何优雅地在两种数据库中穿梭？

经历了这次的“毒打”与反思，我整理了这份经验，送给同样在 MySQL 和 PG 之间游走的你：

**1. 如果你在写 MySQL**
*   **认怂**：老老实实评估字段长度，用 `VARCHAR(n)`。
*   **规矩**：`n` 设置得越小越好，别动不动 `VARCHAR(255)` 或者 `TEXT`。
*   **大文本分离**：如果真的是存一篇文章，用 `TEXT`，但记得**绝对不要**让它在高频查询中参与 `ORDER BY`。

**2. 如果你在写 PostgreSQL**
*   **大道至简**：默认无脑用 `TEXT` 或者不带长度的 `VARCHAR`，性能绝对没问题。
*   **保持清醒**：如果业务有严格的长度要求（比如身份证号），别偷懒，用 `VARCHAR(18)` 或者加个 `CHECK` 约束把门。
*   **抛弃定长**：永远不要用 `CHAR(n)`，除非你真的需要补齐空格。

**3. 核心觉悟：约束前置**
不论用什么数据库，AI 没告诉你的是：数据库不仅仅是用来“存”数据的，更是用来“守住”数据底线的。**如果你去掉了（或省略了）存储引擎层面的长度约束，请务必在业务层或数据库的其他约束（如 `CHECK`）中把它补回来。**

这一次，我不仅弄懂了 `TEXT` 和 `VARCHAR` 的底层差异，更从师傅身上学到了最重要的那一课——**敬畏数据，把约束做在前面**。而这，是任何 AI 都无法直接替代的成长。
