这里面其实藏着两个核心机制：**Docker 的“千层饼”结构** 和 **Harbor 的“按内容去重”逻辑**。

---

### 第一层逻辑：Docker 镜像是怎么堆出来的？

Docker 镜像不是一个完整的、打包好的 `.zip` 或 `.iso` 文件，而是**由一层层的“只读文件系统”叠加起来的**。我们叫它 **Layer（层）**。

*   **底层（Base Layer）**：通常是操作系统（如 Ubuntu）或运行环境（如 JDK、Node.js），可能占了 950MB。
*   **中间层（Dependency Layer）**：你安装的依赖包（如 `npm install` 或 `pip install`），占了 40MB。
*   **顶层（App Layer）**：你写的业务代码或编译后的二进制文件，只有 10MB。

所以，一个 1GB 的镜像，实际上是由这 950MB + 40MB + 10MB 堆起来的。

### 第二层逻辑：为什么 50 个镜像只存一份基础层？

假设你用同一个基础镜像（比如 950MB 的 JDK 环境），构建了 50 个不同版本的应用。

*   每次构建时，如果你的 **基础镜像没有变**，Docker 就不会重新下载或打包这 950MB 的底层，而是直接**复用**已有的。
*   你每次修改代码，只会产生一个新的 10MB 的顶层。
*   而且，**镜像层是有唯一的“身份证号”的（就是 SHA256 值，你截图中左侧那串 `sha256:eeaa41dc...`）**。只要这 950MB 的底层被计算过一次哈希值，之后所有基于它构建的镜像，都只会“引用”这个哈希值，而**不会复制**物理文件（**共享的唯一铁律：哈希值（SHA256）必须完全一样**）。

所以，50 个“1GB”的镜像，在服务器硬盘上的真实物理结构是：
**1 份 950MB 的底层（共享） + 50 份 10MB 的代码层（独立） + 50 份 40MB 的依赖层（可能共享） = 大约 1GB 到 3GB 的物理空间。**



### 第三层逻辑：Harbor 是怎么算账的？

如果在 Harbor 里，每个镜像都显示 1GB，那 50 个加起来就是 50GB。但实际上，Harbor 不是按“镜像清单”的累加来算，而是**按“底层数据块（Blob）”来算**。

Harbor 底层有一个基于内容寻址的存储系统（类似 Git 的原理）：
1. 当你上传一个新的镜像时，Harbor 会先检查它的 SHA256 值。
2. **如果这个层（比如那 950MB 的基础层）在仓库里已经存在了，Harbor 就会直接把文件指过去，不再占用新空间。**
3. Harbor 后台统计存储配额时，会**自动做去重**。无论这 50 个镜像怎么引用这个基础层，在项目配额统计里，这个基础层**只算一次**。

这就是为什么你看到：列表里每个镜像标着 1.66GiB（比如你截图里的那些），但整个项目或仓库的占用总显示只有 9G 左右。因为大家**共享了绝大部分的“地基”**。

### 举一反三（为什么会有些“坑”？）
这个机制虽然省空间，但也解释了运维中常见的坑：
1. **删除镜像是“假删除”**：如果你删除了其中一个镜像，那个 950MB 的底层**不会立刻消失**，因为其他 49 个镜像还在用它。只有当所有引用它的镜像都被删了，垃圾回收（GC）才会清理它。
2. **单独改基础镜像会“爆盘”**：如果你突然把基础镜像从 Ubuntu 换成了 CentOS，那原来的底层就“断供”了。新传的镜像会彻底再存一份 950MB 的基础层，那时候存储空间就会瞬间暴涨。

**总结一句话：列表里的体积是“逻辑体积”（它看起来有多大），Harbor 显示的 9G 是“物理体积”（它实际占了多少硬盘）。** 这就是云原生容器技术“内容寻址 + 分层复用”最精妙的地方。
